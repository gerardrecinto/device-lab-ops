One healthy device per job.

A device farm pool for an ML hardware lab. Jobs lease a device over a REST API. The pool probes it first, expires the lease if the job crashes, quarantines a device that keeps failing, and stops handing out devices from a host whose NFS mount hangs.

Source on GitHub Real output Capacity planner

Leases that expire

One active lease per device, enforced by a partial unique index in SQLite. A crashed job loses its device when the lease runs out.

Health-gated acquire

Every candidate is probed before it is handed out. A failing device is skipped and sorts last. Three failures in a row quarantine it until a person returns it.

Hosts, not just devices

Disk space and NFS mounts are checked on the x86 hosts. A stale mount would hang stat, so the check runs in a child process with a timeout.

Splunk and Prometheus

Probe results become Splunk HEC events (file or direct POST). /metrics serves pool counts in Prometheus text format.

Capacity planner for the next hardware cycle

Same formula as devicelab plan, and a test checks the two agree. Working devices = jobs per day x minutes x peak / (1440 x target use). Spares are added on top, then hosts, then one spare host.

Run it

git clone https://github.com/gerardrecinto/device-lab-ops
cd device-lab-ops && pip install -e .
devicelab demo
devicelab init && devicelab lease job-1 --model gen1
devicelab serve   # REST API on 127.0.0.1:8080

What it is not

  • Not run on physical hardware. The tests and demo use a simulated adapter. The shell adapter runs any command you give it (for example adb -s {serial} get-state) and is covered by tests with stand-in commands.
  • One SQLite file, one process group. Fine for one lab. A multi-site setup would move the same schema to PostgreSQL.
  • No built-in scheduler. Jobs ask for a device; they do not queue.
